# Volume V Threat and Failure Model

**Status:** Design-time extension; no Phase 13/14 controls are implemented by this document. Test strategies below are local, synthetic and non-production.

| Threat / failure | Boundary and impact | Required mitigation / detection | Residual risk and future local verification |
|---|---|---|---|
| Vulnerable, abandoned or malicious dependency | Build input → application/release; code execution, data exposure or compromised artifact | Inventory direct/transitive components, licenses and maintenance; review provenance; prioritize reachable/exploited issues; bounded exceptions with owner/expiry; validate artifact evidence | Unknown zero-days remain; local dependency fixture reports, exception-expiry test and SBOM review |
| Compromised build or tampered artifact | Source/build identity → release consumer; substituted software or false provenance | Least-privilege build; artifact digests; builder-generated provenance; signed manifest/assets; independently verify expected source/builder/signer and parameters | Trusted builder/identity still may be compromised; local signed synthetic artifact verification and negative identity/digest tests |
| Missing or leaked secret / invalid rotation | Deployment secret provider → app/partner; unauthorized access or outage | References only; fail closed if required secret unavailable; short cache; rotation overlap, revocation and redaction; restrict management/config exposure | Provider compromise and memory exposure remain; fake provider rotation, expiry, startup and log scans |
| Publicly exposed or misconfigured management endpoint | Operator network → actuator/admin surface; information disclosure or control compromise | Minimal endpoint allowlist; separate/protected operator plane; safe public health response; production configuration rejects dev profile/open access | Reverse proxy mistakes remain possible; local production-profile reachability and response checks |
| Abusive caller or resource exhaustion | Client/partner → API, SSE, federation or exchange; resource starvation or data enumeration | Scoped authorization plus per-class identity/tenant/partner/operation budgets, bounded payloads/connections/queues, timeouts, pagination and alerts | Distributed abuse may exceed local limits; local synthetic concurrency and exhaustion tests |
| Database failure, disk exhaustion or corrupt restore | App/DB/storage boundary; loss of coordination truth or unsafe partial recovery | Backups independent of replica; WAL/archive/disk monitoring; declared RPO/RTO; isolated restore and workflow invariant proof; readiness fail closed; documented restore authority | Disaster beyond tested assumptions remains; disposable PostgreSQL restore/corruption/space-boundary exercises |
| Failed migration or replica version skew | Release → schema/instances; partial writes, unavailable service or irrecoverable state | Pre-upgrade backup; single migrator; supported version path; readiness/mutation gate; expand/contract where overlap needed; forward repair or restore | Unexpected lock behavior under scale; local interrupted migration and two-version deployment simulation |
| Duplicate workers / process death | Two replicas → DB/outbox/reconciliation; duplicate effect or stuck work | Existing durable claims, fencing, idempotency, outbox; bounded shutdown; no memory-only correctness state | Lease/clock bugs; run local multi-replica duplicate and kill/restart scenarios |
| IdP, peer or external exchange unavailable | App dependency boundary; authentication or remote operations stop | Dependency-specific readiness, clear pending/unknown status, no liveness cascade, bounded retry and reconciliation; core local state remains accurate | Extended outage requires operator process; local IdP/peer failure and recovery simulations |
| Audit failure or log/audit confusion | Mutation → audit store / operator; lost accountability or false claim of persisted audit | Preserve frozen atomic audit rules; distinct audit, logs, traces; fail closed where required; alert audit persistence failure; restricted retention | Recovery of separate non-mutating denial records remains bounded by existing policy; local store-failure test and evidence review |
| Backup/configuration or signing key unavailable | Recovery/release verification; data cannot be restored or artifact trust cannot be checked | Document independent config/secret/key recovery; test verifier and key rotation; avoid storing secrets in DB backup | Loss of external key provider may delay recovery; fake provider/key lifecycle restoration test |
| DPG/open-source claim overstates evidence | Project governance/public statements; false assurance, rights or user harm | Dated criterion evidence matrix; distinguish partial, absent and governance evidence; rights-holder license decision; no DPG claim before owner approval | DPGA criteria may evolve; compare current official questionnaire in future assessment |
| Retention deletion erases required audit/disclosure/idempotency history | Operator retention action → owner history; broken accountability, duplicate operation or privacy differencing gap | Category ownership and retention matrix; immutable evidence dependencies; pseudonymize/minimize only through owner-reviewed procedure | Legal requirements conflict by jurisdiction; synthetic lifecycle and history-continuity review |
| Performance optimization changes policy output | Candidate query/cache path → Matching/owner state; unsafe outcome or inconsistent authorization | Profile first; versioned golden corpus, source/policy identity, property/equivalence assertions and rollback | Corpus may not cover rare edge cases; adversarial synthetic equivalence testing plus review |
| Model hallucination, omission or automation bias | Advisory provider → operator; wrong documentation or misplaced authority | One low-risk use case; explicit label/source links; abstention; no-model path; rejectable non-blocking human review; no mutation permission | Human may over-trust plausible answer; local evaluator tests unsupported claims and reviewer comprehension |
| Prompt injection or indirect content attack | Query/retrieved documentation → model; disclosure or policy influence | Treat text as untrusted; no tools, secrets, arbitrary retrieval/network or owner access; fixed input/output schema and deterministic authorization | Prompt injection cannot be perfectly prevented; local malicious synthetic docs/queries and marker scan |
| Model/provider compromise or data retention surprise | Provider boundary; disclosure, malicious output or third-party training | Model disabled by default; approved versioned provider profile and data terms; minimal documentation-only input; secret references; provider review; incident disablement | External provider trust remains deployment-specific; local fake contract plus configuration deny-list/disable tests |
| Biased or unrepresentative output | Evaluation corpus/user population; uneven quality or harm | Use-case-specific subgroup/language coverage and error review; thresholds/accountable owner; defer when evidence insufficient; no fairness claim | Small corpus may hide disparities; synthetic stratified test and review of limitations |
| Stale advisory or unreviewed model change | Cached answer/config update; misleading support or silent regression | Bind result to corpus/model/template/policy versions; reject stale result; changes re-evaluated and approved; rollback/disable | Nondeterministic inference cannot be exactly replayed; local stale version and change-trigger tests |
| External-service leakage during acceptance | Test environment → public health/model/cloud service; prohibited mutation or data exposure | Local-only target allowlist, deterministic fake, no external credentials; default deny public egress in acceptance where practical | Misconfigured test can still escape; inspect configured host, local network policy, and run acceptance offline |

## Cross-cutting rules

- Deployment controls must be testable and observable, not merely named in a runbook.
- Residual risk, accountable owner and operating assumption accompany each selected deployment profile or intelligence capability.
- The threat model is not a penetration-test result, security certification, legal assessment or DPG determination.
- No external target or model provider is used by future acceptance. Any future external use requires separate authorization and deployment governance.
