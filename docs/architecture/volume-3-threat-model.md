# Volume III threat and failure model

**Status:** frozen design baseline for Phases 8–10; no implementation exists. This model assumes every external system can be unavailable, stale, incorrect, duplicated, compromised, misconfigured, slow, or malicious. It is not a penetration-test report or jurisdictional compliance claim.

## Trust boundaries

```text
Human or local client
        ↓ authentication + AyuVahak authorization boundary
AyuVahak owner contexts and private persistence
        ↓ owner application contract / internal event boundary
Context-owned external adapter
        ↓ shared technical partner trust / egress boundary
Independently administered partner, registry, clinical source, or EMS provider
```

The source is authoritative only for its declared information category. Valid FHIR, a signed partner token, mTLS, an HIE route, or a schema-conformant provider message does not prove truth, freshness, local authorization, identity match, or safe business meaning.

## Threat and failure cases

| Threat / failure | Boundary and impact | Mitigation | Residual risk | Local verification |
| --- | --- | --- | --- | --- |
| Caller-controlled URL / SSRF | API or payload can reach loopback, private services, metadata endpoints, or attacker hosts | Destinations only from administrator-controlled partner config; canonical origin/path; scheme/port allowlist; inspect every DNS answer per attempt and bind the socket to a vetted address while preserving hostname TLS verification; reject loopback/link-local/metadata; private ranges require explicit deployment allowlist; no arbitrary redirects; egress firewall. FHIR absolute references are not fetched unless separately configured. | Resolver, HTTP-client, proxy, and deployment egress behavior must preserve the vetted-address binding; network policy mistakes remain possible. | Local HTTP stub verifies caller URL rejection, loopback/link-local/metadata block, redirect-to-private/origin change, DNS-rebinding time-of-check/time-of-use simulation, actual peer address pinning, approved private partner exception, credential non-forwarding. |
| Endpoint discovery confused with trust | A malicious/stale FHIR Endpoint or mCSD record directs credentials or data to an attacker | Treat discovered endpoints as untrusted metadata; require separately reviewed partner trust profile and exact permitted operations. | Operator can approve a malicious origin or mistake an identifier. | Endpoint fixture cannot initiate request; configuration must independently allow exact origin and operation. |
| Credential or token theft | Partner credentials/tokens leak through storage, logs, crash data, metrics, or cross-origin redirect | Secret references only in ordinary config; operator-managed secret provider; short-lived tokens; bounded cache; asymmetric client auth where partner supports; TLS/hostname validation; no token logging; no cross-origin credential forwarding; rotation/revocation. | Endpoint compromise, host compromise, or compromised secret provider remains a deployment risk. | Synthetic keys/tokens; inspect logs/errors; expiry, wrong audience/issuer, key rotation/revocation, redirect tests. |
| Partner spoofing / wrong issuer | Unauthorized external actor forges status or inbound message | Bind inbound identity to configured partner, operation, organization scope, TLS/auth issuer/audience and key; validate signature/time/algorithm; owner rechecks local operation and Transfer link. | A compromised but valid partner can still send plausible false information. | Wrong cert/key/issuer/audience/scope, revoked partner, wrong transfer reference, and valid-but-conflicting source fixtures. |
| Compromised or mistaken partner | Valid message carries incorrect, stale, contradictory, or excessive data | Preserve source/observed/received times, version, provenance; owner semantic checks; explicit conflict/unknown; source precedence; never overwrite stronger/newer owner fact without policy. | Human/source data quality cannot be eliminated by syntax validation. | Stale, future-skewed, duplicate-version contradictory, and conflicting-source fixtures produce explicit reconciliation. |
| Malformed or malicious FHIR | Parser exhaustion, unsafe references, wrong profiles, polymorphic deserialization, semantic confusion | Pinned version/profile; safe parser configuration; bounded size, depth, resources, references, pages and elapsed time; no unrestricted polymorphic type loading; profile + owner semantic validation; no arbitrary reference fetch; unsupported release fails explicit. | A validator cannot prove clinical correctness, intent, truth, or complete profile coverage. | Malformed JSON, unsupported version/profile, hostile references, nested/large bundle, unknown required codes, duplicate identifiers, and valid-but-contradictory resources. |
| XML external entity / entity expansion | If a partner requires FHIR XML, parser may read local files, make network requests, or consume resources | XML is not baseline-required. If enabled for a named partner, disable DTD, external entities, XInclude, expansion, and external schema retrieval; enforce depth/size limits; local schemas only. | Parser/library defects may persist. | Synthetic XXE/entity-expansion fixture must be rejected with no filesystem/network access. |
| Replay / duplicate inbound exchange | Replayed message repeats cancellation, assignment, movement, or disclosure side effect | Namespaced partner message identity, content fingerprint, owner-local consumer dedup and command idempotency; nonce/time freshness for any specifically agreed signed webhook; same ID/different content is a conflict/security record. | Partners may not provide stable IDs; timestamps are insufficient by themselves. | Exact duplicate returns prior outcome; same ID/different fingerprint rejects; missing identity follows explicit operation policy; replay window and key rotation test. |
| Lost response after external side effect | Partner commits a request but AyuVahak times out; blind retry can double-dispatch | Stable exchange operation ID and partner idempotency key/status query where available; otherwise `OUTCOME_UNKNOWN`, reconcile before retry. Keep owner state separate from delivery state. | If provider offers no safe lookup/idempotency, operator reconciliation may be required. | Mock commits side effect then drops response; same key recovers prior result or state remains unknown without second side effect. |
| Over-broad patient disclosure | Recipient, partner, or generic adapter receives more clinical information than needed | Transfer confirms selected active recipient; Referral separately authorizes purpose/legal hooks and audits before response; allowlisted transient summary; no recipient-membership shortcut; no raw payload persistence. | Local policy/jurisdiction may be incomplete or wrong; operator configuration requires governance. | Deny wrong recipient/purpose/no grant/audit failure; response field allowlist; search database/log/event/audit/telemetry for synthetic marker. |
| Patient-reference collision or misassociation | Same textual identifier across issuers could attach another person's record | Preserve issuer/system, resource type, optional case/encounter scope; never merge by text; exact source-scoped reference and authorized context only. | Source itself may misidentify its own patient. | Same value under distinct issuers remains distinct; mismatch/conflict never falls back to a different patient. |
| Stale mCSD or capacity source | Old facts appear current and affect destination discovery/readiness | Provenance, source version, observed/received time, freshness policy, complete-scope marker; missing/partial query is not deletion; unknown/stale cannot yield positive readiness. | Source may falsely timestamp a stale value or fail to signal correction. | Delayed response, incomplete pagination, cursor restart, deactivation/delete, absent resource, and stale evidence cases. |
| Partner revocation during retry | Queued action keeps using revoked endpoint or cached token | Check trust status/version immediately before each attempt; revocation invalidates token cache, blocks queued retries, and leaves unknown remote outcome for reconciliation. | A request already in flight may complete after local revocation. | Suspend/revoke during backoff and in-flight timeout; no next send; resulting remote uncertainty is explicit. |
| Transport status impersonation | Forged provider event changes Transfer to `IN_TRANSIT` or Arrival | Partner-bound identity, message signature/transport auth, operation/scope and active request check; Transfer validates own chronology; manual source has functional grant and audit. | Compromised authorized provider or human may report false real-world state. | Wrong-provider status rejected; valid provider but wrong transfer/request rejected; authorized manual event works with full attribution. |
| Duplicate/out-of-order movement | Late `ASSIGNED` or duplicate arrival overwrites real later status | Source sequence/version and event/received time; monotonic state rules; immutable observations; owner dedup; reconciliation for impossible transitions. | Provider may omit sequence or timestamps; manual reconciliation remains necessary. | Reorder assignment/onboard/en-route/arrival events and verify state does not regress/skip safety preconditions. |
| Location privacy / surveillance | Precise vehicle coordinates reveal patient route, facility activity, or crew movements | No continuous GPS ingestion by default; only origin/destination and ETA/status needed; no raw location metrics; future location feature requires a separate purpose, rate, retention, role, and review decision. | Facility and time can still be sensitive operational facts. | Search persistence, events, logs, metrics, traces for coordinate paths; reject excess frequency/precision if a future named use exists. |
| Log/metric/trace leakage | Patient IDs, payloads, tokens, or high-cardinality case IDs become broadly accessible telemetry | Allowlisted metadata; redact by construction; no body/header/query logging; metrics only bounded partner/operation/status labels; audit separate and payload-minimal. | Framework exceptions or operator-added instrumentation can regress. | Synthetic secret/patient marker search across captured local logs, metrics, traces, and Problem Details; architecture/config review. |
| Unauthorized cross-context persistence access | Adapter or Transport bypasses owner policies and causes split-brain | Domain-owned ports; architecture rules forbid domain HTTP, FHIR in domain, cross-context repository/table access; owner command and event only. | Reflection/raw JDBC can evade package-level rules if tests are weak. | Compile-time architecture tests plus source/dependency review; test forbidden fixture where the frozen enforcement supports it. |
| Webhook forgery | A generic externally exposed callback can invoke owner commands | No generic webhook receiver is included. A future named callback requires partner-specific route, signed/mTLS identity, replay window, body limits, operation scope, and owner contract. | A later partner requirement may add attack surface. | Acceptance for current design asserts no generic callback; future contract tests local only. |

## Failure taxonomy and safe outcomes

Network/DNS/TLS failure, timeout, rate limit, remote 5xx, authentication failure, authorization failure, revoked partner, malformed/oversized input, unsupported profile/version, semantic mapping error, local policy denial, replay/duplicate, stale/conflict, and unknown remote outcome remain distinct classifications. Retry is bounded and only for plausible transient outcomes with safe idempotency/recovery. Invalid credential, invalid payload, semantic error, revocation, and policy denial are not retried indefinitely. A non-response is not proof that the remote operation failed.

Core Volume II state remains valid when a soft integration fails. Existing Directory projections are labeled with provenance/freshness. IPS source failure returns explicit unavailable/partial context. Transport-provider failure uses pending/manual/exception/unfulfilled status and does not invent a vehicle, departure, arrival, or cancellation. A new hard prerequisite may be introduced only by a future approved phase specification with a safe fallback.
