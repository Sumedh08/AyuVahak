# Phase 1 Engineering Decisions

These decisions constrain Phase 1, which owns only the engineering substrate: repository/build foundation, Maven project/bootstrap, architecture-boundary enforcement, runtime configuration, PostgreSQL/PostGIS connectivity, migration infrastructure, API and HTTP/error/request conventions, testing infrastructure, observability foundation, CI quality gates, local Docker Compose development, and Phase 1 system verification. They do not authorize implementation of business functionality.

Phase 1 must not implement authentication, authorization, organization/execution context, audit, provenance framework, domain-event framework, transactional outbox, event dispatcher, idempotency infrastructure, consumer deduplication, business bounded contexts, or healthcare workflows. Phase 2 owns core domain primitives and those platform-kernel, identity, and trust capabilities; business bounded contexts and workflows belong to later phases. This document does not define business APIs, database tables, FHIR mappings, event payloads, or production topology. Any change to a settled architectural choice requires a documented rationale and, for durable boundary changes, an ADR amendment or superseding ADR.

**Research retrieved:** 2026-10-08. See the read-only [engineering source register](../../.scratch/phase-0-remediation/engineering-research.md). Recheck version-sensitive support facts when Phase 1 pins dependencies. The chosen major/minor lines below are settled; patch dependencies must be pinned in the repository build when implementation begins.

## Selected baseline

| Decision | Phase 1 baseline | Reason for AyuVahak |
| --- | --- | --- |
| JDK | Java 25 LTS, vendor-neutral distribution. | It is an LTS release and inside Spring Boot 4.1's published Java 17–26 range. Java 27 is newer but outside that Boot line's supported range on the research date. The LTS gives a stable contributor and maintenance baseline without selecting a vendor. |
| Spring Boot | 4.1.x; use the latest supported 4.1 patch at Phase 1 bootstrap and pin it. | The 4.1 line is stable and compatible with JDK 25. Boot 3.5.16 was announced as the final open-source 3.5 release. Boot 4.1.1 was current on the research date; no exact patch is frozen here because Phase 1 begins later and must recheck current support/security updates. |
| Build system | Apache Maven, Maven Wrapper pinned to 3.10.0 at bootstrap. | Maven's named lifecycle and reactor make build order and multi-module intent visible with less task-graph configuration. Both Maven and Gradle support multi-module builds; no performance or popularity claim decides this choice. Maven 4 was still a release candidate, not the stable baseline. |
| Migration system | Flyway Community with versioned SQL migrations. | SQL keeps PostgreSQL and PostGIS changes reviewable and explicit. The current reviewed Flyway support matrix included PostgreSQL 18; Liquibase 4.33's cited OSS matrix stopped at PostgreSQL 17. This moving compatibility fact supports, but does not alone determine, the selection. Use forward fixes or a restore for recovery; do not depend on inverse migrations. |
| Persistence | Spring JDBC with explicit SQL as the default. No ORM/jOOQ hybrid in the initial baseline. | Coordination needs explicit transaction and query behavior, PostGIS operations, and clear context-owned persistence. JDBC avoids an ORM unit-of-work hiding database behavior and avoids an additional generated-schema/custom PostGIS mapping layer. Repository interfaces stay inside their owning context. |
| Boundary enforcement | ArchUnit rules run in CI. Spring Modulith is not a Phase 1 requirement. | ArchUnit already satisfies Phase 1's required executable dependency-boundary checks. AyuVahak should not add another architecture framework without demonstrated value. Spring Modulith may be reconsidered later if its module verification, module testing, event publication, documentation, or observability capabilities provide concrete benefit. |
| Module/package structure | One build module initially; package by business context, with context-local `domain`, `application`, and `adapter` seams. Shared `platform` packages contain technical support only. | This is the least complex structure that makes business ownership visible. Separate Maven modules or Java Platform Module System modules can follow if compiler isolation becomes necessary. Do not create repository-wide `controller`, `service`, `repository`, or `model` layers. |
| Internal identifiers | UUIDv4 generated by the JDK for internal entity IDs. | UUIDv4 is available without another generator and avoids placing an approximate creation timestamp in exposed identifiers. Initial deployment accepts its less-local index insertion pattern; benchmark before revisiting. IDs are opaque references, never authorization. |
| API versioning | URI major version, beginning with `/api/v1` when public HTTP APIs are introduced. | Version is visible in logs, browser/network tools, and partner configuration. Increment only for an incompatible public contract; compatible additive changes remain within the current version under documented compatibility rules. No business endpoint is designed here. |
| API errors | RFC 9457 Problem Details (`application/problem+json`) with documented extensions for stable AyuVahak error code, correlation ID, and optional safe field-level validation issues. | It gives clients a standard machine-readable error shape while allowing stable domain error codes. Validation may identify a field and violated constraint, but must not echo patient values; never expose credentials, stack traces, or internal infrastructure details. |
| Database ownership | One PostgreSQL database initially, with logical schema ownership per business context. Create a context's schema and migrations only when that context is implemented; no direct cross-context table access, joins, or foreign keys. | Schema ownership makes accidental sharing visible and keeps operational deployment simple. Other contexts consume an owner's public application interface or explicit event/projection. Database permissions are defense in depth; ArchUnit and review enforce code-level boundaries. |
| Future event concept (Phase 2+) | Internal events use stable names shaped as `<context>.<fact>.v<major>` (for example `referral.referral-created.v1`), immutable facts, and explicit correlation/causation metadata. | This constrains later event contracts; it is not Phase 1 implementation scope. The producer owns event meaning and evolution. Consumers tolerate duplicates and unknown additive metadata; breaking semantic or payload changes use a new major event version and an explicit transition. No event platform or payload schema is selected here. |
| Testing | Unit, architecture, persistence integration, API integration, configuration/bootstrap, and observability smoke checks. PostgreSQL/PostGIS behavior uses disposable local containers through Testcontainers or equivalent. | Real PostgreSQL semantics matter for transactions, SQL, extensions, and spatial behavior; H2/SQLite are not substitutes for those checks. Partner boundaries use mocks, stubs, and synthetic fixtures, never public healthcare systems. |
| Local development | Java 25, Maven Wrapper, and Docker-compatible local runtime for Compose and container-backed integration checks. Pure unit/architecture checks run without containers. Node is needed only when a frontend phase begins. | A contributor should not need Kubernetes, Kafka, a service mesh, proprietary cloud, external healthcare server, or real credentials. Use synthetic local configuration and developer-controlled disposable dependencies. Docker Desktop is one option, not the required vendor. |

## Evaluations behind the choices

### Build: Maven or Gradle

Both provide multi-module dependency graphs. The comparison uses official tool capabilities, not popularity or a claim that one is universally better.

| Criterion | Maven | Gradle | AyuVahak assessment |
| --- | --- | --- | --- |
| Reproducibility | Wrapper pins the Maven distribution; named lifecycle phases and reactor ordering are explicit. | Wrapper pins Gradle; task graph and configuration are more programmable; build cache is optional and disabled by default. | Both can be repeatable when wrappers and dependencies are pinned. Maven's fixed lifecycle is easier to inspect for the initial one-module monolith. |
| Dependency management | POM declares dependencies/plugins and Maven resolves the graph through the lifecycle. | Build scripts declare dependencies and configurations; Java Library separates API from implementation exposure. | Both meet the need. AyuVahak does not yet need Gradle's richer dependency/task configuration. |
| Contributor familiarity | XML POM and conventional lifecycle; contributor familiarity still varies by team. | Kotlin/Groovy DSL and task model; contributor familiarity varies by team and language. | No target team evidence justifies assuming either is more familiar. Maven avoids adding a second scripting language as an initial decision. |
| Multi-module support | Reactor orders modules from declared dependencies. | Multi-project build defines root and subprojects with dependency/task relationships. | Both support later module separation. One build module is selected now. |
| CI predictability | Standard lifecycle gives a stable set of named phases/goals. | Flexible task graph allows targeted tasks and caching, with more configuration choices. | Prefer Maven's smaller configuration surface for agent-authored changes and straightforward CI. |
| Tool complexity | Fixed model and plugin configuration can be verbose but has fewer custom execution paths. | Powerful task model and plugins add useful flexibility and a larger configuration surface. | Maven's constrained model better supports reviewability and guardrails at this scale. |
| Agentic maintainability | Conventional files and lifecycle are easy to inspect and modify locally. | DSL, plugin APIs, and task configuration require more context about the build model. | Choose Maven; this is a judgment from the present scope, not a claim that Gradle is unsuitable. |

Use Maven 3.10.0 through the Maven Wrapper at bootstrap, after rechecking the current stable release. Reassess only with measured build constraints or a demonstrated module-isolation need.

### Migrations: Flyway or Liquibase

| Criterion | Flyway | Liquibase | AyuVahak assessment |
| --- | --- | --- | --- |
| Migration transparency | Versioned SQL scripts are a direct, ordered record of PostgreSQL changes. | Structured changelogs or SQL changelogs; structured change types can be more database-neutral. | Choose versioned SQL so PostgreSQL/PostGIS behavior is directly reviewable. |
| PostgreSQL support | Reviewed support matrix listed PostgreSQL 12–18 and uses a PostgreSQL database module. | Reviewed OSS 4.33 support page listed PostgreSQL 12–17, with 12 deprecated. | Flyway had the broader cited range on retrieval date; recheck this moving compatibility fact at bootstrap. |
| PostGIS | Does not install PostGIS binaries; SQL can enable the extension if server files are present. | Does not install PostGIS binaries; SQL or change definitions can enable an installed extension. | Neither supplies the extension. Pin a PostGIS-capable local/deployment image separately and verify migrations against it. |
| Rollback philosophy | Versioned migration history; undo is optional and Teams-only in the cited docs. Forward fixes and restore are the dependable operational strategy. | Generates rollback for some modeled changes, but not all; SQL often needs authored rollback. | Choose forward fix or restore after a failure. Do not assume any tool can reverse destructive data changes reliably. |
| Java integration | Java library and build integration; PostgreSQL support requires the database module. | Java library with Maven/Gradle integration. | Both fit the selected Spring/Maven stack. |
| OSS/community constraints | Flyway Community core is published under Apache License 2.0; the no-cost Community edition is distinct from paid Teams/Enterprise functionality. | Liquibase Community 5.0 uses the Functional Source License (FSL), which is source-available but not OSI-approved open source; Liquibase 4.x used Apache 2.0. | Choose the Apache-2.0 Flyway core and compatible community PostgreSQL module to fit AyuVahak's open-source goal. Do not rely on paid undo or licensing-gated features. Verify each pinned artifact's license. |
| Operational simplicity | Small versioned SQL migration model with explicit order and validation. | Flexible changelog formats and more change-type/rollback metadata. | Flyway is simpler for one PostgreSQL database and context-owned SQL migrations. |

Choose Flyway Community with versioned SQL. This decision uses its Apache-2.0 core license and PostgreSQL community support as well as its explicit SQL migration model. Liquibase remains a technically capable alternative, but the current Community license differs from its historical 4.x Apache-2.0 license. PostGIS server files come from the selected PostgreSQL image/host; a migration may enable an already-installed extension but cannot supply it. Pin and verify the Flyway PostgreSQL database module along with Flyway itself.

### Persistence: JPA/Hibernate, jOOQ, or JDBC

| Criterion | Spring Data JPA/Hibernate | jOOQ | Spring JDBC |
| --- | --- | --- | --- |
| Domain modeling | Maps entity graphs and managed persistence-context lifecycle; can encourage persistence-shaped aggregates. | SQL-oriented records/types generated from database schema; domain objects can remain separate. | Domain and persistence records are explicit; mapping is maintained at repository boundaries. |
| Explicit SQL and complex operational queries | Supports native SQL, but ORM behavior and query selection need deliberate control. | Builds explicit, composable SQL and generates schema-aware types. | SQL is fully explicit and works for complex PostgreSQL queries; compile-time SQL checking is not built in. |
| PostGIS | Possible through Hibernate spatial support, with version/extension mapping to verify. | Custom converters/bindings may be needed because listed PostgreSQL extensions do not include geometry/geography. | Can use PostgreSQL/PostGIS SQL directly; mapping is explicit and tested against PostGIS. |
| Migration control | Separate migration tool still owns schema history. | Generation depends on schema, so migrations still own schema history. | SQL and migrations remain explicit; repository SQL stays close to owning context. |
| Transactions | Unit-of-work/persistence context gives managed changes and has lifecycle semantics. | Executes JDBC transactions; clear transaction APIs but generated mapping layer exists. | Uses Spring transaction boundaries and JDBC; no ORM entity lifecycle. |
| Modular ownership | Requires strict limits to prevent shared entity graphs and cross-context lazy access. | Schema generation can make cross-context schema visibility tempting; code generation scope must be bounded. | Each context's repository can own explicit SQL and schema without generated shared types. |
| Developer complexity | Familiar abstractions but lifecycle, loading, and flush behavior add concepts. | SQL DSL and generation pipeline add codegen and custom type concepts. | Requires SQL/mapping discipline but keeps runtime and mental model narrow. |

Spring JDBC is selected for the first baseline. Do not add JPA or jOOQ opportunistically to the same context. Revisit with representative query and domain-model evidence, and preserve the single owning repository boundary if a later decision justifies another approach.

Choose Spring JDBC only for the initial baseline. Do not add JPA or jOOQ opportunistically to the same context. Revisit with representative query and domain-model evidence, and preserve the single owning repository boundary if a later decision justifies another approach.

### Modularity: enforcement options

| Option | Enforcement and cost | Decision |
| --- | --- | --- |
| Spring Modulith | Provides module verification and may provide module testing, event publication, documentation, or observability capabilities. | Not a Phase 1 dependency: ArchUnit already meets the required executable dependency-boundary checks, and another architecture framework should not be added without demonstrated value. Reconsider later if these additional capabilities solve a concrete need. |
| ArchUnit | Checks compiled dependency rules for packages, layers, cycles, and forbidden dependencies; does not create separate compile classpaths. | Use in CI now. |
| Separate Maven modules | Strong compile-time dependency boundaries and explicit reactor graph; more build and visibility configuration. | Start with one build module; add only if evidence shows package rules are insufficient. |
| JPMS modules | Compile/runtime module boundaries through `module-info.java`; additional module configuration and library compatibility work. | Do not require initially; reassess if compile-time isolation is needed. |
| Package-level conventions only | Simple but dependent on reviewer discipline and easy to violate. | Insufficient alone; ArchUnit makes rules executable. |

ArchUnit rules run against compiled production classes in the ordinary Maven verification lifecycle. Phase 1 actively checks that production packages contain only implemented platform technical concerns, package slices are acyclic, and any domain package remains independent of Spring, persistence APIs, healthcare integrations, and prohibited infrastructure libraries. A minimal test-source fixture with a deliberate domain-to-Spring dependency proves that the domain rule detects the violation; it is excluded from production package checks and is not a fake business module.

Rules for adapter direction, context public APIs, and preventing one business context from importing another context's persistence internals activate when real business contexts exist. Those rules must inspect the actual compiled context packages when introduced. Until then, they are documented constraints, not claimed executable proof. No empty production package is created to make a future rule appear active. CI fails when any active rule is violated.

### Internal identifiers

| Option | Sortability/index behavior | Exposure, interoperability, and complexity | Decision |
| --- | --- | --- | --- |
| UUIDv4 | Random insertion order; less locality for a B-tree index. | JDK supports generation directly; no timestamp is encoded; common 128-bit format. | **Choose for internal entity IDs.** Initial index cost is acceptable; measure before revisiting. |
| UUIDv7 | Time ordered and can improve index locality. | Encodes approximate creation time; Java 25 has no built-in generator, requiring a selected library or maintained implementation. | Do not add generator/timing leakage without measured need. |
| ULID | Lexicographically sortable when generated appropriately. | Distinct encoding/format and generator semantics; also exposes approximate time. | Avoid an extra identifier format and dependency at baseline. |
| Database-generated numeric IDs | Compact and naturally indexed within one database. | Sequential and enumerable when exposed; distributed creation requires more coordination; should not be partner IDs. | Not selected because internal references may be created in multiple integration paths and must remain opaque. |

External resource IDs remain scoped by issuer and resource type; business identifiers retain assigning authority; correlation IDs identify an event chain, not a person. No ID grants access.

### HTTP contract conventions

| Concern | Alternatives | Decision and reason |
| --- | --- | --- |
| Versioning | URI major version such as `/api/v1`; media-type/header versioning; unversioned endpoints with compatibility policy. | Use URI major version. It is visible in operational tooling and straightforward for public/open-source integration. Use compatible additive evolution within a major version; make an incompatible contract a new major URI. |
| Error representation | Custom envelope; RFC 9457 Problem Details; another application-specific format. | Use RFC 9457 `application/problem+json`, with stable error-code and correlation-ID extensions and optional safe field-level validation issues. It preserves standard members while adding machine-usable domain meaning. Details identify a field/constraint without echoing patient data or leaking internals. |

No business route, request shape, or error catalog is defined in Phase 0.

### Database ownership

| Option | Consequence | Decision |
| --- | --- | --- |
| One shared schema with ownership by convention | Simple migrations and queries, but names and permissions do little to expose ownership; direct cross-module reads are easy. | Not selected. |
| One schema per business context in one PostgreSQL database | Makes ownership and migration responsibility visible while keeping a single deployment/database. Cross-schema joins and foreign keys must be prohibited by code review and CI rules. | **Selected ownership policy; create a schema and migrations only when its owning context is implemented.** |
| Separate database per context | Stronger runtime isolation but creates distributed transaction, operations, backup, and deployment costs. | Premature for the initial monolith. |

No context may treat another context's tables as its public API. No cross-context joins or foreign keys. Read through the owning context's API or explicit event/projection. The initial shared application database identity means schema privileges are defense in depth; executable package rules and migration ownership remain necessary.

## Conceptual repository/package shape

This is a long-term package ownership map, not source code or a scaffold:

```text
monorepo/
  backend/                         # one Maven build module initially
    <root-package>/
      referral/
        api/                        # published context-facing contract
        application/                # use cases and owned ports
        domain/                     # pure Java domain language/rules
        adapter/inbound/            # HTTP or human/system entry points
        adapter/outbound/           # partner and persistence adapters
      directory/ ...                # same local seam, only when implemented
      capacity/ ...
      matching/ ...
      transfer/ ...
      transport/ ...
      notifications/ ...
      identityaccess/ ...
      audit/ ...
      analytics/ ...
      platform/                     # technical support, no workflow ownership
  docs/
```

Phase 1 must not create empty packages, placeholder classes, repositories, interfaces, controllers, migrations, schemas, or adapters for future business bounded contexts merely to pre-create the architecture. This prohibition includes Directory, Capacity, Referral, Matching, Transfer, Transport, Notifications, Analytics, and other healthcare domains. If architecture tests need sample packages to prove ArchUnit rules, use the smallest clearly identified fixture/example under test sources, not fake production domain modules. Business schemas are created only when the owning business context is implemented.

When a business context is implemented in a later phase, its public API is the only supported code-level entry point for another context. Outbound adapters live under the consuming context because that context owns the port and mapping. A partner adapter may use shared transport, authentication, validation, terminology, provenance, and telemetry utilities, but it does not call another context's repository. Domain packages contain no framework or FHIR classes.

## Identifier and event constraints

Keep these identifiers distinct:

- **Internal entity ID:** opaque UUIDv4 issued by AyuVahak for a coordination entity.
- **External resource ID:** value issued by another system, stored with issuer/source and resource type, never treated as globally unique alone.
- **Healthcare/business identifier:** domain or standards identifier whose assigning authority and use are explicit; it is not an internal database key.
- **Correlation and causation IDs:** trace a request/event chain and parent action; they do not identify or authorize a patient.

These are Phase 2-and-later event contract constraints, not Phase 1 deliverables. An event's stable name includes its owning context, fact, and major contract version. Event metadata may carry event ID, correlation/causation IDs, actor/system and organization context, occurred/recorded times, and schema version. Business payload contracts are defined with the owning context when needed; this Phase 0 document does not predefine them. Consumers handle duplicates idempotently. Additive optional information may be introduced compatibly only where the contract says so. Changed meaning or incompatible shape gets a new major version and a planned consumer transition. No Kafka or schema registry is required.

## Phase 1 system verification

Phase 1 verifies only the engineering substrate it introduces. Its system-verification categories are:

1. Reproducible Maven-wrapper builds and CI quality-gate execution.
2. ArchUnit boundary rules, using only implemented production packages and minimal test-source fixtures if required.
3. Transaction and persistence integration checks against production-equivalent PostgreSQL, with PostGIS semantics where applicable.
4. Deterministic runtime configuration and application bootstrap validation.
5. API foundation and HTTP/request/error convention checks, without business endpoints or healthcare workflows.
6. Observability smoke checks for safe diagnostics and correlation without clinical payloads.
7. Repeatable local Compose startup and Phase 1 system verification using developer-controlled local dependencies.

Phase 2 adds tests for authentication/authorization, organization/execution context, audit, provenance, domain events, outbox recovery, idempotency, duplicate protection, and kernel failure/recovery. Later business phases add tests for the domain scenarios and workflows they implement, including stale capacity, recommendations, acceptance, reservation conflicts, transfer reconciliation, and transport. These are not Phase 1 acceptance tests.

Testcontainers is the intended Java integration-test mechanism for disposable local services, subject to Phase 1 compatibility and platform verification. Local mock servers, deterministic fixtures, and controlled containers represent external integrations. Never write to public/demo healthcare services. Do not use H2 or SQLite to claim PostgreSQL/PostGIS behavior.
