# Data Ownership and Authority

## Principle

AyuVahak must not become the system of record for information it does not need to own. Authority is category-specific, not a property of a whole system. AyuVahak owns the coordination state it creates; references, caches, snapshots, and imported facts retain their source, purpose, observation time, and limitations.

Retention durations cannot be fixed until a deployment's jurisdiction, controller/operator roles, consent/legal basis, and recordkeeping requirements are known. The default is purpose limitation and the shortest retention consistent with care coordination, safety, audit, and applicable law. A closed coordination record is not permission to retain a clinical summary indefinitely.

Use these information-handling categories when describing a copy: **reference only** (identifier/link, no copied payload); **transient processing** (validated in memory or an approved short-lived exchange path, then discarded); **bounded transfer context** (minimum patient facts retained only for the active coordination case); **operational state** (AyuVahak-owned workflow facts and attributed evidence); and **aggregate/de-identified analytics** (purpose-approved derived measures with disclosure review). A system's receipt or transport of a payload does not by itself authorize AyuVahak to persist it.

| Medicine/commodity stock | LMIS/OpenLMIS or pharmacy/supply-chain system. | No routine copy. | Authentication identity | External identity provider. | Store subject identifier and minimal session/issuer metadata; never store passwords or private credentials. | Session data expires; retain only security audit metadata under policy. | IdP to AyuVahak via approved federation; revocation and issuer changes are honored. | Deny new authentication; no local password fallback. |

| Audit trail | AyuVahak for actions and access within AyuVahak; IdP/HIE/partner systems remain authoritative for their own logs. | Record attributable action, purpose, target reference, outcome, event/recorded times, and source. | Application and integration logs | AyuVahak for its operational diagnostics; external systems retain their own transport logs. | Operational metadata only, such as component, correlation, outcome, and timing. ## Synchronization rules

- Read external authority into a provenance-preserving view; do not silently write AyuVahak changes back into an external master.
- Export AyuVahak-owned coordination outcomes only to authorized destinations and only for an explicit purpose.
- Never resolve source conflict by last-write-wins without domain-specific authority and human correction rules.
- Distinguish event time from receipt/recorded time. Late information may correct the chronology but must not erase prior evidence.
- Caches are labeled with source, last update, and expiry. A stale value is unknown for safety-critical matching.
- Retention, access, and deletion policies must be configured by a deployment's accountable authority before production use.

## Authority cross-check

The following cross-check keeps the categories used by the system-context, workflow, standards, security, and analytics documents on one authority strategy. “Bounded case” means only the minimum facts needed for the active coordination case are persisted; it does not mean a clinical record copy.

| Concept | Authority strategy | AyuVahak representation |
| --- | --- | --- |
| Patient identity | MPI/client registry where available; otherwise originating clinical system for its local identifier. | External reference plus minimum bounded-case display attributes; no matching/merge authority. |
| Patient demographics | Source EHR/HIS or the registry that owns each attribute. | Bounded-case copy only where necessary; source attribution and correction path preserved. |
| Clinical record | Patient's clinical EHR/EMR. | Reference only; no longitudinal record. |
| Patient summary / IPS | Authoritative EHR/HIS or clinician-authorized source. | Transiently validated and, when necessary, bounded to the active transfer context. |
| Clinical attachments | Source EHR/HIS or document repository. | Reference only in the initial baseline; no persistent binary attachments. |
| Practitioner identity | Workforce IdP/directory for workforce subject; provider registry for official professional identifiers. | Minimal subject/reference data with issuer and purpose. |
| Practitioner authorization | Deployment authority sets grants; AyuVahak enforces local application policy. | Operational authorization state and attributable grant history; no credential certification. |
| Facility identity | Official facility registry where present, otherwise accountable deployment authority. | Attributed coordination projection/reference. |
| Service directory | Facility/service registry or accountable health authority. | Refreshable projection with source and freshness. |
| Capability | Facility service owner or accountable facility authority. | Attributed capability profile; distinct from current capacity. |
| Capacity observation | Receiving facility's designated system or accountable source. | Attributed observation with unit and times; stale is unknown. |
| Referral | AyuVahak only when selected as the workflow owner; originating EHR may retain its own referral. | AyuVahak coordination state and minimum patient context. |
| Destination recommendation | AyuVahak for the recommendation it computed. | Evidence snapshot, rule version, reasons, and user disposition. |
| Transfer Request | AyuVahak for the request and recorded response; receiving facility for its decision. | Operational workflow record with external correlation and attributed response. |
| Clinical/operational assessments and Acceptance | Receiving authorities mapped by deployment policy. | Separate attributed assessment facts and a separate Acceptance fact. |
| Reservation | Facility bed/reservation system if integrated; otherwise the locally authorized human authority for a coordination-only commitment. | Commitment and status record; never a physical bed ledger. |
| Transfer lifecycle | AyuVahak coordination history; external sources for reported real-world events. | Operational state plus attributed chronology and reconciliation. |
| Handover acknowledgement | Authorized receiving care-team member or locally designated reporter. | Attributed case fact and chronology; not a duplicate clinical note. |
| Transport assignment | EMS/dispatch authority. | External assignment reference and minimum case status. |
| Ambulance location, if later introduced | Vehicle tracking/dispatch authority. | Not in the initial baseline; future active-case-only, short-lived view. |
| Audit trail | Each system for its own actions; AyuVahak for actions performed in AyuVahak. | Restricted, attributable operational state without clinical payload snapshots. |
| Public-health aggregates | DHIS2 or designated public-health HMIS. | Approved one-way aggregate/de-identified export only. |
| Medicine/commodity stock | LMIS/OpenLMIS or responsible pharmacy/supply system. | No routine copy or transaction; future signal only under a separate decision. |
| Authentication identity | External IdP. | Subject and issuer reference; no password storage. |
| Application authorization | Accountable deployment defines policy; AyuVahak enforces it. | Local grants and policy history, distinct from authentication. |
| Raw FHIR/partner resource snapshot | Partner system that issued the resource. | Transient processing only; no general raw-resource archive. |
| Application diagnostics | AyuVahak for its own operational events. | Minimized metadata; no clinical payload or secrets in normal logs. |
| Analytics | AyuVahak owns only derived coordination measures; BI/HMIS owns its broader measures. | Governed, minimized aggregation; no patient-level warehouse. |
