# Volume IV Technical Research

**Retrieved:** 2026-10-17
**Scope:** Official documentation only; DHIS2 aggregate API semantics and authentication/version basis, plus Spring MVC SSE and PostgreSQL `LISTEN`/`NOTIFY` capabilities relevant to a simple local notification design. No running DHIS2 or healthcare/public-health service was contacted. Example URLs and commands shown in upstream docs were read as documentation only and were not executed.

## DHIS2 version and API basis

- The official release index lists DHIS2 v43 as supported and release 43.1.0 dated 2026-08-03. The DHIS2 developer documentation has a version-specific Core 2.43 API reference. This note therefore uses **Core 2.43 / API documentation** as its concrete research basis as of retrieval, not as a decision that every future partner must run 2.43. Sources: [DHIS2 release index](https://releases.dhis2.org/), [Core 2.43 Data API](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/data.html), [Core 2.43 Web API introduction](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/introduction.html).
- Core 2.43 metadata documentation says version-prefixed API paths from versions 28 through 43 are supported, but calls with and without a version prefix behave the same and the project aims to remove version-prefixed calls. **Design choice:** store a tested partner API capability/version basis in deployment configuration and prefer the unversioned `/api/...` path; do not freeze `/api/43` into business code or assume every target shares the same supported release. Source: [Core 2.43 metadata API — Web API versions](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/metadata.html).

## Aggregate data model and DataValueSet

- Core 2.43 documents `POST /api/dataValueSets` for a related group of aggregate data values, with XML and JSON examples. The set-level fields include dataset, period, organisation unit, and attribute option combination; values carry data element, optional category option combination, value, and optional comment. It also documents per-object ID schemes (`uid`, `code`, `name`, or a unique metadata attribute), with the payload-level scheme taking precedence over query parameters and specific schemes taking precedence over the general scheme. Sources: [Core 2.43 Data API — sending and importing data values](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/data.html).
- A DataValueSet identifies values through DHIS2 metadata: data element, period, organisation unit, category option combination, attribute option combination, and value. The documentation shows these dimensions in import/export representations; it does **not** define an AyuVahak operation ID or immutable revision identity. **Design choice:** keep a stable AyuVahak snapshot/revision/export-operation identity locally and resolve each target element, org unit, and dimension through versioned deployment mappings. Never use DHIS2 identifiers as AyuVahak business identity. Source: [Core 2.43 Data API](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/data.html).
- DHIS2 data elements define a domain type (`AGGREGATE` or `TRACKER`), value type, aggregation type, category combination, and `zeroIsSignificant`. The metadata docs say `zeroIsSignificant` indicates whether zero values are stored. Category option combinations (COCs) are generated from a category combination and its categories/options; validation checks the generated combination and uses the COC UID. Period identifiers use explicit formats, and `GET /api/periodTypes` lists available period types; examples include monthly `yyyyMM`, quarterly `yyyyQn`, and financial-year periods. Sources: [Core 2.43 metadata API — data elements and COCs](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/metadata.html), [Core 2.43 Web API introduction — periods](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/introduction.html).
- Organisation units form a parent/child hierarchy and are DHIS2’s geographical aggregation dimension. The official user guide warns that DHIS2 uses the **latest** hierarchy for data aggregation, so changing that hierarchy loses its historical temporal representation. **Design choice:** treat org-unit mapping and reporting-period attribution as deployment-controlled, versioned inputs; do not silently recompute frozen historical AyuVahak snapshots against a later target hierarchy. Source: [DHIS2 Metadata Management — organisation unit hierarchy](https://docs.dhis2.org/en/use/user-guides/dhis-core-version-master/configuring-the-system/metadata-metadata-management-app.html).
- Aggregate DataValueSets are distinct from individual-level Tracker data. Core metadata distinguishes aggregate and tracker data-element domain types, and the separate Tracker API models tracked entities, enrollments, and events. **Design choice:** Phase 12 targets aggregate DataValueSets only; support for Tracker/Event export would be a separate authorization and design decision, not an implementation shortcut. Sources: [Core 2.43 metadata API](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/metadata.html), [Core 2.43 Tracker API](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/tracker.html).

## Import, update, deletion, and reconciliation semantics

- The DataValueSet import options include `CREATE`, `UPDATE`, `CREATE_AND_UPDATE`, and `DELETE`; `dryRun` is also available. The documentation says an unchanged value is ignored when `value`, `comment`, and `followUp` match. It shows an import summary with imported, updated, and ignored counts, and an example where a value referencing an unknown organisation unit is ignored. Thus a successful HTTP exchange must not be treated as proof that every value was accepted. Sources: [Core 2.43 Data API — import parameters and summary](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/data.html).
- The same documentation’s aggregate summary is `imported="2" updated="1" ignored="1"`, but its following prose incorrectly says “zero data values were ignored.” This is an internal documentation inconsistency. The summary reports counts, not a guaranteed mapping from each count to a particular DataValue. **Design choice:** initial Phase 12 requests contain one DataValue so documented counts are attributable to one target tuple; `ignored=1` remains ambiguous and requires authorized read-back or operator reconciliation. A local mock must model only this documented summary contract.
- `DELETE` is an explicit import strategy, and individual data-value deletion is separately documented. DHIS2 describes data values as softly deleted and allows deleted values to be included in reads with `includeDeleted=true`. The docs do not state that omitting a value from a DataValueSet deletes it, nor do they define omission as zero. Data-element metadata separately controls whether zeros are significant/stored. **Design choice:** omission means “not supplied,” never a deletion or zero instruction. Preserve missing/partial source status locally; send an explicit zero only when the approved indicator snapshot says the value is truly zero and the configured target element’s zero behavior is known. Treat deletion as a distinct, explicitly authorized correction workflow. Sources: [Core 2.43 Data API](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/data.html), [Core 2.43 metadata API — data element fields](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/metadata.html).
- Asynchronous imports return a DHIS2 job/task identifier and expose task-summary/status endpoints; summaries can report status and imported/updated/ignored/deleted counts. This is useful only after the caller has received and retained the task identifier. The referenced docs do not promise that a summary remains available across restart or for a specified retention interval. Sources: [Core 2.43 Data API — async import](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/data.html), [Core 2.43 Maintenance API — asynchronous task summaries](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/maintenance.html).
- No caller-supplied idempotency key, conditional compare-and-set, durable operation-status lookup by client key, or exactly-once guarantee is documented for DataValueSet import. Repeating `CREATE_AND_UPDATE` may update the current value for the same target dimensions; an unchanged retry can be ignored, but that is not a concurrency-safe replay contract. A read-back can show current target values but cannot necessarily prove which attempt wrote them if another writer can intervene. **Design choice:** record an immutable local snapshot and stable operation/revision identity; send one target tuple per initial-profile request; treat response loss as `OUTCOME_UNKNOWN`; reconcile only through a named, authorized read-back/partner capability or explicit operator resolution. Never blindly replay an unknown update or overwrite a newer value.
- The examples demonstrate mixed imported/updated/ignored counts, but the DataValueSet documentation does not specify an all-or-nothing transaction guarantee, per-value result mapping for multi-value requests, or the exact committed-state behavior for every mixed validation/error combination. The metadata-import `atomicMode` option is documented for metadata imports and must not be assumed to apply to DataValueSet. **Design choice:** represent partial export as separate one-tuple operation outcomes and do not infer undocumented per-value detail from aggregate summary counts; require local mock cases for imported/updated/ignored summaries, separate operation outcomes, response loss, reconciliation, and correction.

## DHIS2 authentication facts

- Core 2.43 Web API documentation lists Basic authentication, Personal Access Tokens (PATs), and OAuth 2.0. It warns Basic credentials are exposed without TLS and says HTTPS is a hard requirement when using Basic. It calls PATs preferable for new scripts/apps, but PATs inherit the creating user’s authorizations; it recommends a specially scoped user where narrower access is needed. OAuth 2.0 access likewise reflects the DHIS2 user’s roles and is not a fine-grained AyuVahak authorization system. Sources: [Core 2.43 Web API authentication](https://docs.dhis2.org/en/develop/using-the-api/dhis-core-version-243/introduction.html).
- The versioned OAuth section demonstrates registered clients with password, refresh-token, and authorization-code grants. It does not establish that every DHIS2 partner supports a machine-to-machine client-credentials grant or the Phase 9 authentication profile. **Design choice:** Phase 12 must select only an authentication mechanism supported by both the configured target and the frozen Phase 9 exchange capability; default to administrator-provisioned least-privilege credentials stored as references through Phase 9. Never register a client automatically or use the password grant as a shortcut. Do not infer authorization from OAuth scopes or partner identity.

## Spring MVC SSE comparison for Phase 11

- The current Spring Framework reference lists 7.0.9 as stable and documents Spring MVC `SseEmitter` as an asynchronous `text/event-stream` response using Servlet async processing. It is a natural fit for predominantly server-to-browser notification; Spring also supports WebSocket when bidirectional messaging is actually required. Source: [Spring Framework — Asynchronous Requests, HTTP Streaming, and SSE](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html).
- Spring MVC streaming does not itself provide durable event history, replay cursors, resource authorization, or grant-revocation policy. Servlet APIs do not signal client disconnection until a write fails, so the docs recommend periodic heartbeats. Spring MVC response writes are blocking on a separate thread, and its default async executor is explicitly not suitable under production load. **Design choice:** use SSE only as a bounded, non-authoritative notification transport if Phase 11 needs one-way push; notify with opaque resource/version/sequence hints, then fetch current state through the authorized API. Bound per-client queues, disconnect/coalesce slow clients, reauthorize on reconnect and resource fetch, and use HTTP refresh/polling as fallback. No notification is a substitute for the owner database or replay store.

## PostgreSQL notification comparison for Phase 11

- PostgreSQL 18 is the current supported documentation version at retrieval. `NOTIFY` delivers to sessions that have `LISTEN`ed on the same database; notifications are delivered only after the sending transaction commits and the receiving session is not in a transaction. Identical channel/payload notifications within one transaction may be coalesced. The payload is under 8,000 bytes by default; the notification queue can fill and then make a notifying transaction fail at commit. Sources: [PostgreSQL 18 NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html), [PostgreSQL 18 LISTEN](https://www.postgresql.org/docs/18/sql-listen.html).
- `LISTEN` is session-scoped and removed when the session ends. PostgreSQL documents a setup race and recommends committing `LISTEN`, then inspecting database state in a new transaction, then relying on subsequent notifications. These properties make `LISTEN`/`NOTIFY` a useful same-database wake-up signal, not a durable event log or replay mechanism. **Design choice:** retain the existing transactional outbox/event substrate as durable authority and replay source. If `NOTIFY` is used, make it a small post-commit hint to wake a worker; restart, reconnect, cursor, and recovery behavior must read durable outbox/projection state. Do not put business payloads or patient data in notification payloads.

## Research limits and unresolved technical facts

1. The versioned DataValueSet page accepts JSON and XML examples but its import-summary example is XML; it does not clearly specify response representation negotiation for every JSON import path. Resolve the exact response contract against a local controlled mock/fixture for the chosen target profile during implementation; do not use a public DHIS2 instance.
2. The import summary example contains a count/prose contradiction, and the docs do not guarantee per-value mapping or settle atomicity for mixed DataValueSet outcomes. Send one value per initial-profile request; preserve ambiguous `ignored` and response-loss outcomes for authorized reconciliation. Local mocks verify the documented summary, not undocumented remote detail.
3. DataValueSet docs do not specify stable client idempotency, remote operation lookup after a lost response, async-summary retention across restart, omission-as-delete, or universal zero storage. The safe design is explicit revisions, current value read-back only when authorized, and `OUTCOME_UNKNOWN` otherwise.
4. OAuth support is version/configuration dependent; the v2.43 examples show delegated user grants but do not document a universal service-to-service grant contract. Confirm partner support from its approved configuration/documentation before enabling that profile.
5. Spring Framework 7.0.9 and PostgreSQL 18 documentation informs capability comparison only; it does not select a Spring Boot release, deployment capacity limit, event replay implementation, or production throughput target.

## Resulting Volume IV design choices

- **Phase 11:** authoritative owner state stays in PostgreSQL; existing transactional outbox remains durable event/recovery substrate; browser SSE is a candidate one-way hint channel with bounded cursors/reconnect/refresh, subject to authorization and backpressure design. PostgreSQL `NOTIFY`, if used, is only a wake-up signal. No broker, event sourcing, Redis, or shared federation database is justified by these facts.
- **Phase 12:** introduce a versioned aggregate-only export mapping around DHIS2 DataValueSet metadata. Keep immutable AyuVahak aggregate snapshots and revisions separate from mutable DHIS2 current values. Version the indicator, source cutoff/completeness, reporting timezone/period, org-unit mapping, category combination, target data element, and partner configuration. Send one tuple per initial-profile request because the documented import summary is aggregate-only; treat `ignored` and response-loss outcomes conservatively. Use synchronous import only initially; a background task ID cannot clear the durable target-tuple barrier until a separately approved async profile stores and reconciles its terminal status. Preserve stable disclosure lineage across policy revisions and serialize one unresolved operation per DHIS2 tuple so concurrent or delayed writes cannot bypass suppression or apply stale revisions. Missing/partial is not zero; release-set suppression and target-zero policy must pass before export. Reuse Phase 9 trust/SSRF/TLS/auth controls. Public DHIS2 access is never an acceptance dependency; use synthetic payloads and a local deterministic mock only.
