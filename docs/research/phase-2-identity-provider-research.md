# Phase 2 Identity and Provider Research

**Retrieved:** 2026-10-08  
**Scope:** Current, primary-source facts relevant to a local Keycloak reference identity provider, OAuth/OIDC interoperability, and Spring Security JWT resource-server validation. This is a factual source note; it does not select a new product architecture or define implementation details.

## Findings

### OpenID Connect and human identity

- **Standard fact:** OpenID Connect Core 1.0 is an identity layer on OAuth 2.0. It lets a relying party verify an end-user identity based on authentication performed by an OpenID Provider and receive identity claims. The OIDC ID Token represents claims about the authentication event; it is distinct from an OAuth access token used to call a resource server. See [OpenID Connect Core 1.0, incorporating errata set 2](https://openid.net/specs/openid-connect-core-1_0.html), especially §§1, 2, and 3.1.
- **Standard fact:** In OIDC Authorization Code Flow, the client receives an authorization code at the authorization endpoint and obtains tokens from the token endpoint. The provider configuration/discovery mechanism supplies endpoint information; Core assumes the relying party has provider configuration. See [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html), §§1 and 3.1.
- **Standard fact:** OAuth 2.0 Security BCP (RFC 9700) requires public clients using the authorization-code grant to use PKCE; it recommends PKCE for confidential clients. When used, `S256` is the only currently specified challenge method that does not expose the verifier in the authorization request. This is relevant to the future human-client design but does not decide that client architecture here. See [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1).
- **Standard fact:** OIDC does not define AyuVahak's organization/facility access model. Authentication claims may establish a subject identity; application authorization still needs policy and trusted execution context. OIDC Core describes identity claims, while RFC 9068 treats authorization claims as optional and says how they combine with contextual authorization is outside that profile. See [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html) and [RFC 9068 §2.2.3](https://www.rfc-editor.org/rfc/rfc9068.html#section-2.2.3).

### Keycloak as a local reference provider

- **Product fact:** Keycloak documents itself as an OpenID Connect Provider and publishes realm-specific provider configuration at `/realms/{realm-name}/.well-known/openid-configuration`. That gives a concrete local reference for discovery-based provider configuration without making Keycloak-specific endpoints part of AyuVahak's domain model. See [Keycloak: Securing applications and services with OpenID Connect](https://www.keycloak.org/securing-apps/oidc-layers), “Endpoints.”
- **Product fact:** Keycloak's client-credentials support represents access by the client itself, not a human user. Keycloak describes it as an OAuth 2.0 grant (not an OIDC login flow), supports client authentication with a secret or public/private keys, and associates the client with a built-in service account when configured. See [Keycloak OIDC layers](https://www.keycloak.org/securing-apps/oidc-layers), “Client credentials,” and [Keycloak Server Administration Guide 26.8.0](https://www.keycloak.org/docs/26.8.0/server_admin/), “Using a service account.”
- **Product fact:** In Keycloak's service-account model, token roles are constrained by both client role-scope mappings and roles assigned to the service account. The guide recommends configuring scoped roles rather than relying on “Full Scope Allowed” for production. See [Keycloak Server Administration Guide 26.8.0](https://www.keycloak.org/docs/26.8.0/server_admin/), “Using a service account.”
- **Product fact:** Keycloak 26.8.0's `service_account` client scope supplies the `client_id` claim for client-credentials tokens when service accounts are enabled. This supports a configured machine-client identity mapping; it does not make that claim an AyuVahak permission. See [Keycloak 26.8.0 Upgrading Guide](https://www.keycloak.org/docs/26.8.0/upgrading/), “New client scope `service_account` for `client_credentials` grant mappers.”
- **Product fact:** Keycloak has a documented container development mode (`start-dev`) for development/testing, with loopback binding shown in its example. The documentation distinguishes this from production-optimized startup. Therefore the local reference IdP can be run as a developer-controlled test dependency, but a development-mode setup is not a production deployment recipe. See [Keycloak: Running Keycloak in a container](https://www.keycloak.org/server/containers), “Trying Keycloak in development mode.”
- **AyuVahak compatibility implication (inference):** Treat Keycloak as a replaceable reference implementation. Keep provider-specific realm/client setup and claim mapping at the identity adapter/configuration boundary. Define a provider-neutral contract around trusted issuer, signing-key discovery, access-token audience, subject, and whatever minimal authentication claims the application needs. Do not assume every OIDC provider uses Keycloak's service-account, role, or claim conventions.

### Access-token validation and provider compatibility

- **Standard fact:** OAuth 2.0 does not require access tokens to have a particular representation. RFC 9068 defines an optional interoperable JWT access-token profile; if an issuer claims conformance to that profile, its tokens carry the `at+jwt` type and required claims/validation rules. A JWT-looking token must not be assumed to conform to RFC 9068 merely because it is a JWT. See [RFC 9068 §§1, 2, and 4](https://www.rfc-editor.org/rfc/rfc9068.html).
- **Standard fact:** For RFC 9068 JWT access tokens, a resource server validates token type, exact issuer, expected audience, signature against authorization-server keys, and expiry; the profile also requires issuer metadata/JWKS publication recommendations and distinguishes access tokens from ID Tokens. See [RFC 9068 §4](https://www.rfc-editor.org/rfc/rfc9068.html#section-4) and [§5](https://www.rfc-editor.org/rfc/rfc9068.html#section-5).
- **Standard fact:** RFC 9068 requires the `client_id` claim in its JWT access-token profile and says a client-credentials token's `sub` should identify the client when no resource owner is involved. The claim establishes a client identity only under a trusted issuer/profile; AyuVahak still classifies principal kind through explicit issuer/client configuration and performs its own authorization. See [RFC 9068 §§2.2.1 and 3](https://www.rfc-editor.org/rfc/rfc9068.html).
- **Standard fact:** RFC 9700 recommends audience-restricting access tokens to one resource server (or a small set) and requires the resource server to reject tokens not intended for it. It also recommends restricting token privilege to the minimum required. See [RFC 9700 §2.3](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.3) and [§4.10.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.10.2).
- **Standard fact:** RFC 9700 recommends asymmetric client authentication where feasible, including mutual TLS or signed JWT client assertions, because the authorization server need not retain symmetric client secrets. Keycloak documents both secret and public/private-key client authentication options. See [RFC 9700 §2.5](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.5) and [Keycloak OIDC layers](https://www.keycloak.org/securing-apps/oidc-layers), “Client credentials.” This is a future deployment security consideration, not a requirement to select one credential mechanism in this research note.
- **Spring implementation fact:** Spring Security Resource Server supports JWT bearer-token validation using issuer metadata and published JWKs. Its current reference documents issuer (`iss`) and timestamp (`exp`, `nbf`) validation; audience validation can be configured explicitly. A direct JWK Set URI may be supplied while retaining issuer validation; that allows application initialization without contacting the authorization server at startup. See [Spring Security: OAuth 2.0 Resource Server JWT](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html), “Specifying the Authorization Server,” “Specifying the Authorization Server JWK Set Uri Directly,” “Supplying Audiences,” and “Configuring Validation.”
- **Spring implementation fact:** Spring Security 7.1.1 documents an in-memory five-minute default JWK-set cache, configurable through the JWT decoder's cache. It documents RS256 as the default trusted algorithm and supports an explicit allowlist. The local AyuVahak profile can therefore preserve startup independence and cached-key validation without adding a distributed cache; exact outage behavior must still be verified with local tests. See [Spring Security 7.1.1 JWT resource-server reference](https://docs.spring.io/spring-security/reference/7.1/servlet/oauth2/resource-server/jwt.html), “Configuring Trusted Algorithms” and “Configuring Timeouts.”
- **AyuVahak compatibility implication (inference):** The settled locally validated signed-JWT direction narrows the practical provider contract beyond “supports OIDC”: a deployment provider must issue access tokens in a format AyuVahak can safely validate and provide trusted signing-key discovery (or equivalent operator-configured JWK URI), exact issuer identity, and an audience claim usable for AyuVahak. The JWT profile is a useful interoperability target to evaluate, but should be required only if the selected provider demonstrably supports it and the implementation decision adopts it. Do not accept ID Tokens as API access tokens.
- **AyuVahak compatibility implication (inference):** Authorization should not depend on a vendor-specific role claim as the sole source of permission. Provider roles/scopes can be mapped at the boundary, but AyuVahak's scoped authorization grants and organization/facility execution context remain application-owned and must be checked for each protected action. This is consistent with RFC 9068's statement that authorization decisions can depend on resource-server context and are outside the token profile.

## Relevant architecture constraints (not new decisions)

These source facts are consistent with the already settled AyuVahak direction:

- Use an external IdP and keep human and machine identities distinct.
- Use a local Keycloak deployment as a reference/testing provider, while keeping production deployments provider-compatible.
- Treat OIDC authentication, API access-token validation, AyuVahak authorization, and organization/facility execution context as separate concerns.
- Require an access token to be intended for the AyuVahak resource server; do not infer authority from a valid signature alone.
- Keep machine clients separately scoped and attributable. A client-credentials token represents the service/client principal, not an end-user.
- Do not store secrets in source control. Use only synthetic local test configuration and developer-controlled infrastructure.

## Limits and follow-up

- This was documentation-only research. No IdP was contacted, no container was run, no account was created, and no credentials or patient data were used.
- No Keycloak-vs-provider feature parity test was performed. A Phase 2 implementation should verify the local Keycloak reference profile with a local container and synthetic users/clients, then keep interoperability tests at the standards/configuration boundary.
- The companion [authentication version preflight](phase-2-authentication-version-preflight.md) settles the current local candidate versions: Spring Boot 4.1.1 / managed Spring Security 7.1.1 and Keycloak image tag 26.8.0. Implementation must still verify token profile/claim mapping and cached-key outage behavior using local fixtures/containers. Image digest and provenance are to be checked before the local image is first used.
- Browser client topology, deployment credential method, access-token lifetime/revocation window, and deployment-specific role mappings remain outside the Phase 2 implementation baseline or are deployment decisions.
