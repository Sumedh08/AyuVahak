# Phase 11 Spring MVC SSE Implementation Notes

**Retrieved:** 2026-10-17
**Documented basis:** Spring Framework 7.0.9 reference/Javadoc and Spring Boot 4.1.1 system requirements (the current official stable documentation inspected on the retrieval date). Boot 4.1.1 requires Spring Framework 7.0.9 or later. These findings describe the official API contract; they are not a claim about a different application-managed Framework version.
**Scope:** Read-only official Spring documentation/Javadoc research. No application code was changed and no healthcare, federation, or partner endpoint was contacted.

## Verified facts

- `SseEmitter` specializes `ResponseBodyEmitter` for SSE. It supports async request handling with events sent after the controller returns. The emitter accepts a custom timeout; when no timeout is set, the default comes from MVC configuration or the underlying Servlet container. Sources: [Spring Framework 7.0.9 SseEmitter Javadoc](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/web/servlet/mvc/method/annotation/SseEmitter.html), [ResponseBodyEmitter Javadoc](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/web/servlet/mvc/method/annotation/ResponseBodyEmitter.html).
- `send` writes to the response and can throw `IOException`; the emitter serializes concurrent response writes with an internal write lock. If a send fails with `IOException`, Spring says not to call `complete()` or `completeWithError()` for cleanup: the Servlet container reports an async error and Spring MVC completes request processing through its error handling path. Sources: [ResponseBodyEmitter Javadoc](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/web/servlet/mvc/method/annotation/ResponseBodyEmitter.html), [Spring MVC asynchronous requests and SSE](https://docs.spring.io/spring-framework/reference/7.0/web/webmvc/mvc-ann-async.html).
- The emitter provides timeout, error, and completion callbacks. Javadoc states timeout and error callbacks run from a container thread; completion can occur for any reason, including timeout and network error, and is useful for detecting that an emitter is no longer usable. The timeout callback is not documented as itself completing the emitter. Sources: [ResponseBodyEmitter Javadoc](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/web/servlet/mvc/method/annotation/ResponseBodyEmitter.html).
- The Servlet API does not notify an application immediately when a remote client disconnects. Spring recommends periodic writes, such as an empty/comment-only SSE event, so a disconnected connection is detected when a write fails. Spring MVC response writes remain blocking; the reference specifically describes separate-thread writes for reactive streaming, not a general non-blocking guarantee for `SseEmitter`. Source: [Spring MVC asynchronous requests, streaming, and disconnects](https://docs.spring.io/spring-framework/reference/7.0/web/webmvc/mvc-ann-async.html).
- Spring Boot 4.1.1 requires Spring Framework 7.0.9 or above and supports Servlet 6.1+ containers (including its documented Tomcat 11.0.x and Jetty 12.1.x lines). Source: [Spring Boot 4.1.1 system requirements](https://docs.spring.io/spring-boot/system-requirements.html).

## What these facts do not imply

- An SSE write does not prove that a client received, processed, or is still authorized to read the hinted resource.
- An emitter is not a durable queue, replay store, or backpressure policy. The cited contracts do not provide an application-level bound on per-client pending notifications or a guarantee that an application sender cannot block on response I/O.
- Async callbacks are lifecycle signals, not durable event acknowledgements. Their existence does not guarantee instantaneous disconnect detection or instantaneous authorization-revocation propagation.
- Spring MVC's reactive-streaming backpressure discussion does not turn imperative `SseEmitter` sends into non-blocking I/O.

## Phase 11 implementation consequence

Treat SSE strictly as a non-authoritative hint channel. Persist and advance the bounded, scoped notification projection independently of client delivery. Do not call `SseEmitter.send` inside an owner transaction, event/outbox handler, or shared durable-event dispatch loop: response writes can block and one slow/disconnected client must not delay business commits or other subscribers. Fan out only through isolated, bounded per-client queues and bounded delivery workers; coalesce safe same-resource hints or disconnect an overflowing subscriber and require an authorized refresh. Register timeout/error/completion cleanup to remove stale subscriptions, with the completion path as a final cleanup signal; on send `IOException`, stop that subscriber and let the Servlet/Spring async error lifecycle clean up rather than calling `completeWithError`. Configure an explicit connection timeout/lifetime and heartbeat interval; periodically reauthorize according to the Phase 11 specification, because timeout/completion callbacks do not enforce authorization themselves.

**Inference:** Isolation and queue policies above are application design consequences of Spring's blocking response-write and lifecycle contracts combined with Phase 11's frozen requirements for bounded backpressure, replay, authorization, and outbox isolation. They are not Spring-provided guarantees.
