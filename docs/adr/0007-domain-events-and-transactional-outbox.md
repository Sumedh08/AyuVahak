**Amended:** 2026-10-08. An event contract has an owning context, stable `<context>.<fact>.v<major>` name, correlation/causation metadata, occurrence and recorded times, and an explicit compatibility policy. Breaking meaning or shape requires a new major event version and planned consumer transition. No distributed event platform or payload schema is selected. This remains an accepted architecture decision for Phase 2 and later; Phase 1 does not implement domain events, an outbox, or idempotency. Phase 1 engineering scope is summarized in [Phase 1 Engineering Decisions](../architecture/phase-1-engineering-decisions.md).

**Amended:** 2026-10-08 for Phase 2 delivery semantics. Publication is at least once; consumers must be idempotent. There is no global event ordering guarantee. Where causal order is required for one aggregate, the producer assigns a monotonic sequence and a later event must not be considered successfully published ahead of an earlier unpublished event for that aggregate. A blocked aggregate does not block independent aggregates. Command idempotency is separate from consumer deduplication: command receipts belong to the command-owning context, while event receipts belong to each consumer-owning context. No generic cross-context business-state or receipt store is introduced. See [Phase 2 architecture](../architecture/phase-2-platform-kernel.md) and [specification](../specs/phase-2-platform-kernel-spec.md).

# Use domain events and an outbox without event sourcing

Contexts may publish internal domain events when other AyuVahak contexts need to react to committed facts. The publishing context owns the meaning and version of its event. Use a transactional outbox where a committed fact must be reliably published to an asynchronous internal consumer. External delivery remains behind an adapter owned by the context that needs the exchange; the shared event framework/outbox is not a universal integration gateway. Keep current owned state and an appropriate audit history; do not adopt full event sourcing. Use CQRS only for a demonstrated query need and do not start with distributed CQRS or a mandatory Kafka cluster. This provides reliable internal coordination without making every workflow depend on a distributed event platform.
