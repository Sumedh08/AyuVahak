# AyuVahak — Production Readiness Gap Analysis

**Assessment date:** 2026-10-20
**Baseline:** Frozen Volume IV source and acceptance records at the inspected local baseline.
**Purpose:** Identify product-level evidence and remaining operational/deployment work. This is not a deployment approval, security certification or claim of production readiness.

| Area | Status | Existing evidence | Gap and Phase 13 design action | Evidence needed before a live deployment |
|---|---|---|---|---|
| Architecture / topology | PARTIAL | Modular monolith; Compose-first local topology; PostgreSQL/PostGIS; OIDC boundary; architecture contracts and frozen phase records. | Define single-site and HA institutional profiles, failure domains, portability and operational ownership; no mandatory Kubernetes. | Select profile and validate environment-specific network, DB, IdP, ingress and operator design. |
| Availability and SLO | MISSING | Quality attributes avoid unsupported universal uptime claims; Actuator health/readiness exists. | Provide configurable SLI catalogue, SLO declaration/evidence format, alert and response model. | Deployment selects numeric objectives/windows and proves them under its workload. |
| Capacity/performance | PARTIAL | Testcontainers and acceptance scenarios exercise correctness; no general production throughput envelope asserted. | Baseline synthetic benchmark variables and measurement record before optimization or scale claim. | Run representative load on chosen topology, set limits, alert thresholds and headroom. |
| PostgreSQL backup | PARTIAL | PostgreSQL is authoritative; persistence/migration and restart behavior are tested. | Specify backup scope, protection, WAL/PITR options, configuration coverage, retention and archive monitoring. | Deploy backup job/target, encryption/access, off-host copy, recovery keys and monitoring. |
| Restore / RPO / RTO | MISSING | Restart and local database tests exist; no production-profile full restore acceptance evidence identified. | Deployment-declared RPO/RTO and mandatory isolated synthetic restore drill checking workflows/invariants. | Measured restore time/data-loss boundary meets approved target; named recovery owner and drill cadence. |
| Upgrade / migration recovery | PARTIAL | Ordered Flyway migrations and full clean verification exist. | Supported version paths, pre-upgrade backup gate, controlled migrator, mixed-version sequencing, interrupted migration recovery. | Exercise upgrade and rollback/forward-repair procedure on deployment-like copy. |
| Multi-replica / shutdown | PARTIAL | Durable outbox, idempotency, SSE and operation claims provide seams; local app is containerized. | Explicit duplicate-worker two-replica proof and bounded graceful shutdown/recovery criteria. | Validate across chosen load balancer/worker topology. |
| Identity / authorization | PARTIAL | OIDC resource-server validation, local grants, scoped service identities, audit and local Keycloak acceptance. | Production profile issuer/JWKS/rotation/runbook and IdP failure controls; protected admin/management plane evidence. | Configure and test organizational IdP, key rotation, break-glass and role/grant governance. |
| Secrets / keys / TLS | MISSING | Phase 9 has secure partner-secret references and endpoint/TLS controls; Compose examples are explicitly local. | Production-wide provider-neutral secret resolution, fail-closed startup, rotation/expiry/revocation and certificate runbooks. | Integrate selected external secret provider and TLS lifecycle; never use committed values. |
| API / abuse limits | PARTIAL | Authentication, validation, bounded payloads, endpoint safety and safe API conventions exist. | Route/identity/scope/partner-specific rate and resource budgets, including SSE/admin/federation/exchange. | Configure ingress and application limits from measured budgets; run abuse/resource tests. |
| Security verification | PARTIAL | Threat models, ArchUnit, local security acceptance, Phase 9 SSRF/TLS and Phase 12 privacy controls exist. | Versioned OWASP ASVS 5.0.0 evidence matrix, exclusions, production-profile negative tests and periodic review. | Deployment assessment and targeted external security review under separate authorization. |
| Dependencies / vulnerabilities | PARTIAL | Maven Enforcer and pinned framework/runtime/dependency versions provide build controls. | Dependency inventory, maintenance/license review, vulnerability prioritization, exception and remediation policy. | Run approved local/CI tooling, triage findings and assign remediation owners. |
| Build/release provenance | MISSING | CI runs clean verification; Docker bases and local infra images are digest-pinned. | Release artifact SBOM, provenance, signature/manifest, trusted identity and verification instructions. | Produce/verify evidence for an actual release; no SLSA-level claim before proof. |
| Containers / updates | PARTIAL | Non-root runtime and digest-pinned images are documented; Compose is loopback-bound. | Supported production image profile, Java/base image cadence, digest rollout and emergency update process. | Operator chooses image source/platform, verifies digest and applies updates. |
| Observability / alerts | PARTIAL | Actuator, Micrometer, structured logs, trace bridge, Prometheus endpoint and PHI-minimization tests exist. | Define SLI dashboard/alert classes, backlog age, audit/unknown outcomes, access/retention and deployment routing. | Install and test selected monitoring backend, alert routing and escalation. |
| Incident/runbooks | MISSING | Failure semantics exist in architecture, threat models and acceptance docs. | Operator runbooks for database, IdP, secrets, external unknown outcomes, backlog, audit, disk, migration, breach and dependency incidents. | Name on-call/response roles, contact paths, exercise and review runbooks. |
| Retention/deletion | PARTIAL | [Data ownership](../architecture/data-ownership.md) and [Volume IV data ownership](../architecture/volume-4-data-ownership.md) define minimization and several owner-specific lifecycle invariants; the proposed [Volume V retention matrix](../architecture/volume-5-retention-governance.md) classifies each owner/category and its purge/history dependencies. Durations intentionally remain unspecified. | Implement owner-controlled expiry, purge/minimization, holds, restore propagation and evidence reporting from the matrix; no common cross-owner deletion job may bypass owners. | Controller/authority and records/privacy owner choose lawful purpose/duration, review holds, and validate operational evidence and audit/history effects. |
| Governance / privacy | DEPLOYMENT-SPECIFIC | AGENTS and frozen privacy/security docs define product safeguards and synthetic-only development. | Product-level and operator-facing privacy notices, accountability and incident evidence. | Identify controllers/operators, legal authority, purposes, consent where relevant, cross-border limits and breach process. |
| DPG / open source governance | MISSING | Extensive public-facing engineering docs and a DPG research basis exist. | No license, public project owner/rights statement, CoC/safeguarding route, vulnerability disclosure contact or DPG evidence pack. | Rights-holder, maintainers and governance owners make and publish decisions; no claim inferred from design. |
| Documentation / support | PARTIAL | README, contributor guide, API/architecture/spec/acceptance docs are extensive. | Production deployment, upgrade, backup/restore, security, support, troubleshooting and adopter guides. | Validate docs with operators/adopters; publish support/ownership model. |
| Portability / accessibility | PARTIAL | Open standards, vendor-neutral ports and no frontend requirement are documented. | Dependency/substitution inventory, general non-PII data portability guide, standards/accessibility register. | Assess selected deployment, documentation accessibility/localization and any future user interface. |

## Status counts

There are 21 rows: **READY 0**, **PARTIAL 13**, **MISSING 6**, and **DEPLOYMENT-SPECIFIC 2**. The assessment is a design-time gap view; Phase 13's specification requires future evidence rather than changing a status by intention alone.

## Basis and limits

Primary-source research and version facts are in [Volume V production/security/supply-chain research](../research/volume-5-production-security-supply-chain-research.md) and [DPG Standard research](../research/volume-5-dpg-standard-research.md). The matrix distinguishes existing repository evidence from deployed control operation. A frozen acceptance record shows tested local behavior, not an external deployment's lawful configuration, operating history, support, backup service or SLO.
